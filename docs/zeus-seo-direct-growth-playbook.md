## Приоритет 1 — устранить технические препятствия индексации

1. Контролировать фактическую публикацию на REG.RU, коды 200, 301, 404, размер и скорость ответов, зеркала, canonical, отсутствие noindex/блокировки роботов, мобильную доступность.
2. Поддерживать один актуальный sitemap.xml с **только реальными URL**; lastmod проставлять исключительно при существенных правках. Не отправлять неизменённый sitemap десятки раз в день.
3. Проверить, что на статью можно попасть обычной HTML-ссылкой с библиотечной страницы и хотя бы одной тематической страницы, а не только через фильтр на JS.
4. Сравнивать страницы, которым Google присвоил «URL unknown», «Discovered — not indexed» и «Crawled — not indexed»: это разные сценарии. Для unknown — проверять обнаружение и публикацию; для crawled — ценность контента и дубли.
5. Сайт <10 тыс. страниц; упор на качество, структуру и серверную доступность, а не «кроулинговый бюджет».
6. Отправка на переобход Яндекса: проверять текущую очередь и выдерживать временные сбои HTTP 504; не создавать дубли заявки без необходимости. IndexNow уведомляет поисковые системы, но не гарантирует индексацию.

## Приоритет 2 — редакционная SEO-программа для практикующего судебного юриста

- Приоритет — страницы коммерческого намерения: судебное представительство, жилищные, семейные, земельные, наследственные, арбитражные и трудовые споры; отдельно — тематические юридические разборы.
- Кластеры поисковых задач: «юрист по [типу дела]», «оспорить [решение] в суде», «апелляция по [делу]», «судебный представитель [Москва, МО и другие обслуживаемые регионы]», конкретные основания и процессуальные документы.
- На каждой статье — уникальный точный Title / H1 / description, ясная постановка проблемы, алгоритм действий по ГПК/КАС/АПК, доказательства, типичные ошибки, разграничение случаев, проверенные нормы и дата актуализации, раскрытое авторство. Не добавлять вымышленные судебные решения, рейтинги и отзывы.
- Связать информационные статьи с релевантной страницей услуги через спокойный CTA; текст должен помогать читателю независимо от покупки.
- Структурированные данные — только подтверждаемые: Article, Person, BreadcrumbList, Service, FAQ только если есть реальные соответствующие разделы. Schema.org не является гарантией попадания в расширенные результаты.
- Избегать шаблонного массового переписывания статей, переспама, спрятанных ключей, покупных ссылок, поддельных сигналов опыта.

## Приоритет 3 — Яндекс Директ + SEO + Метрика

1. Услуги/спрос/ключевые фразы сгруппировать по типам споров и стадиям дела; отделить коммерческий интент от общих учебных запросов.
2. Подготовить посадочные страницы под проверенные юридические услуги, а не вести весь платный трафик на общую библиотеку статей.
3. Проверить ограничения объявлений, соответствие сайту, реальные цены, географию оказания юридических услуг, релевантные минус-фразы («бесплатно», «вакансия», «образец скачать», когда запрос нецелевой).
4. Метрика — четыре цели (звонок, MAX и две автоцели). Уточнить реальные конверсии: звонок соединён, качественный диалог, заключён договор. Настроить UTM и передачу офлайн-конверсий только при достаточной правовой базе и безопасной обработке ПД.
5. Отчёт по источникам: показы → клики → визиты → контакт → квалифицированный лид → договор; стоимость квалифицированного лида и договора, а не только CPC/CTR. Для недостаточных данных явно писать «не хватает выборки».
6. Подготовка рекламных кампаний и исследований разрешена. **Запуск платных кампаний, изменение бюджета, автосписания и платежи — только с отдельного согласия владельца.**

## Роли и доступы

- **Google GSC:** подтверждён через GSC Wizard; GA4 не подключён (нет Analytics scope у текущего аккаунта), для этого нужна отдельная авторизация Google Analytics.
- **Яндекс Вебмастер и Метрика:** прямой OAuth через GitHub Actions работает. Яндекс Директ: отдельный доступ Direct API или кабинет под владельцем, до этого — только публичные исследования и подготовка настроек. Не добавлять Direct write в общий вебмастерский секрет.
- **REG.RU:** исходники публикуются через cron; для административных изменений ISPmanager/зон DNS необходим ограниченный серверный аккаунт либо узкий API-доступ, выданный лично владельцем. Не запрашивать root-пароль, мастер-токены и не публиковать секреты в репозитории.
- **Отчёты:** ежедневная проверка с фактами и ссылками на GitHub-коммиты, отдельно поисковые данные, отдельно реальные заявки.
